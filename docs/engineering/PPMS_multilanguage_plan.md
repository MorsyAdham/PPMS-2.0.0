# PPMS Multi-language Plan

PPMS is used by teams working in English, Korean and Arabic. This document records the decisions, how the interface translation works, the review workflow and the stages still to do.

It applies to all vehicle types (K9, K10, K11) and to every module (KD1, F200-KD2, F100-KD2).

## 1. Decisions (October 2026)

| Topic | Decision |
|---|---|
| Languages | English (default), Korean (한국어), Arabic (العربية) |
| What is translated now | The interface only: menus, buttons, labels, messages, tooltips |
| What users type | Not translated for now. See section 7 for the later plan. |
| Plan data | Never translated: station, part, unit and battalion names, codes, people's names |
| Arabic digits | Western digits (0–9) |
| Arabic direction | The page is right-to-left. The Gantt timeline and the VPX matrix stay left-to-right, because time and process order run left to right. |
| Who translates | The Korean and Arabic drafts are written in PPMS. Native-speaker reviewers correct them in the Excel review sheet. |
| Language choice | Each user picks the language from the globe button next to the notifications bell, in the user menu, or on the sign-in page. It is saved on the user's profile (migration 60) and in the browser. |

## 2. How it works

- **`app/scripts/core/i18n.js`** is the translator.
  - `_t('English text', { n: 3 })` returns the text in the user's language.
  - The English text is the key, so a missing translation shows English instead of breaking.
  - It also sets `lang` and `dir` on the page, loads the Korean or Arabic font (Noto Sans KR or Noto Sans Arabic) only when needed, and formats dates in the user's language with Western digits.
- **`app/scripts/i18n/strings.js`** holds the translations: one entry per English text, with its area plus Korean and Arabic. It is generated by the tools below, so don't edit it by hand.
- **`app/styles/features/i18n.css`** holds the language picker, the font fallbacks and the right-to-left rules. Arabic letters are joined, so `letter-spacing` is switched off in Arabic.
- **Classic scripts** (`app.js`, `kd2.js`, `gantt-module.js`) use the global `_t`. ES modules import it from `core/i18n.js`. If an older cached page loads without the translator, `app.js` and `kd2.js` fall back to English.
- **Loading screen:** its text is in `index.html`, before any script runs. Each text carries `data-i18n="English text"`, and `core/i18n.js` translates it as soon as it loads. A small script at the top of `index.html` sets the page direction from the saved language first, so Arabic users don't see the screen flip. The progress messages in `app.js` go through `_t`.
- **Placeholders** such as `{n}`, `{b}`, `{name}`, `{done}` and `{total}` are replaced by numbers or names on screen. They must be kept exactly as written in every language.

## 3. Review workflow

1. **Export the review sheet:** `python tools/i18n_export.py` writes `docs/translations/PPMS_UI_translations.xlsx`.
   - The **Translations** sheet has the columns Area · English · Korean · Arabic · Reviewer notes.
   - It also includes a **Glossary** sheet and a **How to review** sheet.
2. **Review:** one reviewer per language edits only the Korean or Arabic column, and adds questions in Reviewer notes.
3. **Read the reviewed sheet back in:**
   - `python tools/i18n_import.py reviewed.xlsx --dry-run` shows what would change.
   - Run it again without `--dry-run` to write the changes.
   - Rows whose placeholders don't match the English are rejected and listed.
4. **When new interface text is added in code:**
   - Run `python tools/i18n_extract.py > extracted.json`, then `python tools/i18n_build.py extracted.json`.
   - This adds the new texts, keeps the existing translations, and lists anything still untranslated or no longer used.
   - Texts that reach `_t()` through a variable (move hints, status names, filter labels) are listed in `DYNAMIC` in `i18n_extract.py`.

## 6. Database

`database/migrations/60_user_preferred_language.sql` adds `planning_app_users.preferred_language` (`en` / `ko` / `ar`).

- It only adds a column, so older app versions ignore it.
- Until it has run, the language is saved only in the browser.
- After it has run, the choice follows the user to any device: it is read at sign-in and saved when the user switches.

## 7. Later: translating what users type

Not built yet; recorded here so it isn't lost.

- **What:** production issues (title, description, proposed solution, action taken), comments, remarks and delay reasons.
- **How:** translate when the text is saved and store the translations next to the original, in a new additive translations table.
  - Readers see their language, with "Translated from … · Show original".
  - The original stays the official text, and editing it re-translates.
- **Service:** a translation service with a glossary, so station names, codes and shop terms stay exact. Claude is recommended for manufacturing text; Google or DeepL are alternatives.
  - The service key must stay on a server, which fits the Vercel / secure-version plan.
- **Before building:**
  - confirm with security / IT that issue text may be sent to an outside service, and which one;
  - decide which fields are translated.
